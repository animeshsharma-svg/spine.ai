Part 1 — The settings problem

What "settings" means

Each customer has one revalidation configuration. It says which vendors get checked, which documents, how often, and from when. It is a normal custom configuration row:

  • Table custom_configurations, key vendor_revalidation_config, item_type = "Company", item_id = 47053 (GMMCO's row is id 21842). The value sits in modifications.value.
  • The engine reads it through Company#vendor_revalidation_config (app/models/company.rb:920, via CustomConfiguration.cached_all_configs). Revalidation is "on" only when the customer is on vendor onboarding v2 and enabled == true (company.rb:925-927).

GMMCO's current value (set by ops on 15 Oct):

{
  "enabled": true,
  "vendor_statuses": ["active", "invited"],
  "validations": {
    "gst":  { "paths": ["form.gstin", "company.gst_no"],  "frequency": "quarterly", "start_date": "2026-10-15" },
    "pan":  { "paths": ["form.pan_no", "company.pan_no"], "frequency": "yearly",    "start_date": "2026-10-15" },
    "msme": { "paths": ["form.msme_no"],                   "frequency": "one_time",  "start_date": "2026-10-15" },
    "bank": { "paths": ["form.bank_account_no"],           "frequency": "quarterly", "start_date": "2026-10-15" }
  }
}

Field meanings: vendor_statuses = which buyer–vendor link statuses are checked (active, invited, onboarding_in_progress, in_review, in_approval, rejected, blacklisted, in_active). paths = where a document value is read from, tried in order (form.<field> = the onboarding v2 form, company.<column>, company.misc.<key>, company.extended_fields.<key>; a bank entry can be an object with bank_account_no and ifsc paths). frequency = one_time, monthly, quarterly, six_monthly, yearly. start_date = first due date; cycles count from it.

What changed on 20 Oct, and why QA is stuck

  1. Until 20 Oct there was a private QA API: GET/PUT /api/vendor_revalidation_qa/config. It let a tester save a customer's settings, and it validated them (unknown statuses, unknown document types, bad frequency, bad date, bad path syntax were refused with a clear message). Commit 0f365a7e52 ("revamp apis") deleted that controller and all of those checks. Nothing replaced them.
  2. The only remaining way to save this key is the general endpoint POST /api/custom_configuration/update_or_create (app/controllers/api/custom_configuration_controller.rb). Its policy allows a super admin or a Procol employee (custom_configuration_policy.rb), but before saving it calls MasterConfiguration.config_key_exists(item_type, key, user) (app/models/master_configuration.rb:65-75), which only returns true when the master entry's visibility is "visible" or the user is a Procol employee. The master entry for this key (master_configurations id 835) is not visible. So a customer's super admin gets 422 {"code":1103,"message":"The Config type is not supported"}. We confirmed this live with GMMCO's super admin (user 20030): the identical current value was refused.
  3. "Procol employee" means user.company_id == Rails.application.config.procol_employee_company_id (user.rb:749-755). On UAT that is ENV["PROCOL_EMPLOYEE_COMPANY_ID"], defaulting to 500 = "Procol Traders" (config/environments/staging.rb:41). Every account in that company is a real Procol person; QA has none.
  4. Because the checks were deleted, whatever a Procol employee saves is accepted as-is (REV-17). A typo such as "frequency": "weekly" or "start_date": "15-10-2026" is stored; the nightly scheduler then skips that document type and only writes a config_error log line (scheduler_worker.rb:92). The customer's vendors silently stop being re-checked.

What to ask the developer (settings)

  1. Give QA a way to change settings on UAT. Either an account in company 500 ("Procol Traders") for QA, or set PROCOL_EMPLOYEE_COMPANY_ID on UAT to a company that holds a QA account, or make the master entry for vendor_revalidation_config visible to super admins on UAT only. Any one of these unblocks 26 tests, which then run on their own with the settings saved and restored around each test.
  2. For tonight only (if 1 takes longer): set GMMCO's config to the value below before 22:00 IST and put the current value (above) back tomorrow morning. This makes the 23:00 nightly run check only the "rejected" group — 62 Procol test vendors with fake documents and 5 real ones, roughly 90 cheap provider calls — with every document type due that day. One night then covers the schedule, coverage, GST/PAN/MSME/bank outcome and listing cases.

Part 2 — REV-19: a run that has vendors to check never starts

What a buyer sees

Click "revalidate now" (the dashboard's call to POST /api/vendor_validation/trigger?workspace_id=47053). The API answers 200 with a job id and a run id. Then nothing: the run's status stays "scheduled", zero rows are created, no vendor is checked, no error is shown anywhere, and the status keeps saying "scheduled" for 7 days (the job-state TTL).

The last row matters: a scheduler-mode request with nothing due does finish. So the job is taken from the batch_low queue and TriggerWorker#perform runs; the crash is in the part that only runs when there is work.

Database evidence: vendor_validation_histories has no row dated 2026-10-20 or 2026-10-21 for client 47053, although seven runs were accepted. The vendors' link rows were not reset either.

The code path

  1. Api::VendorValidationController#trigger validates the request, then TriggerService.schedule saves the job state scheduled in Redis (vendor_revalidation:trigger:job:<jid>) and pushes VendorRevalidation::TriggerWorker onto batch_low (trigger_service.rb schedule).
  2. TriggerWorker#perform (trigger_worker.rb, sidekiq_options retry: false) builds TriggerService.new(...) and calls #call.
  3. TriggerService#call (trigger_service.rb:31-50): finds the client, select_vendors, due_doc_types — this far works (the nothing_due case gets through it) — then
    • reset(chosen): VendorValidationHistory…delete_all for the run date and vendors; BuyerSellerCompanyMapping…update_all(vendor_validation_status: nil, …); $redis.del(*lock keys); $redis.del(summary key); delete_jobs(vendor_ids), which iterates Sidekiq::Queue for vendor_revalidation, vendor_revalidation_retry, batch_low plus Sidekiq::ScheduledSet and Sidekiq::RetrySet, reading job.args[0], job.args[1], job.args[2] of every job;
    • RunWorker.perform_async(...);
    • save_state(jid, 'state' => 'started', …).
    The state never reaches started, so #call raises somewhere between the start of reset and save_state. With retry: false the exception is not retried, nothing is written to the job state, and the API keeps reporting the stale scheduled.

Where to look first

  • Sidekiq Web → Dead on UAT: with retry off, a failed VendorRevalidation::TriggerWorker lands there with its backtrace. Job ids: 1ceeac833123d7ae8b151d9e, e2bfc669fb5b7d6fd79aa360, 336d40bacccec22600527906, 3b6c30e5da1a991a78f47e89, 2fe3919526069d33c1750fcc.
  • Logs around the times above for TriggerWorker / [VendorRevalidation] trigger_fired (never printed) and any exception.
  • Likely culprits, in the order we'd check: delete_jobs hitting a job in the scheduled or retry set whose args is not an array (e.g. a job of another class with keyword args), so job.args[2] or job.args[1] raises; $redis.del(*keys) on a client that does not accept several keys; a very large ScheduledSet making the worker exceed a timeout; the partial_run write in RunWorker (the column exists on UAT, so unlikely).

What to ask the developer (REV-19)

  1. Find and fix the raise in TriggerService#call (Dead set first).
  2. Wrap the work in a rescue that does save_state(jid, 'state' => 'failed', 'error' => e.message), so GET /runs/:id?job_id= tells the truth; today a buyer is told "scheduled" for a week.
  3. Make delete_jobs only delete VendorWorker jobs for the chosen vendors, not every RunWorker of the run (REV-09: two triggers started together can delete each other's run).

Once this is fixed, the 20 blocked tests run on demand in about 25 minutes (npm run reval:run -- --company 47053) with screenshots, no scheduler needed.
