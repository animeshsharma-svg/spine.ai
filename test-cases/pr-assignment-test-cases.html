PR Assignment Test Cases

What really decides who appears in the assignee list, who can see a PR, and what the assignee receives — with 46 test cases the product team can run or hand to QA.

The two questions, answered from the code

1. "Is the user mapped to the category only not visible, or the one mapped only to the sub-category?"

Neither. The assignee list never looks at categories. When you click the person+ button the dashboard asks the backend for users who are members of a team of type Purchase — nothing about the PR's category, nothing about the team's categories. So a user mapped to a parent category and a user mapped only to a sub-category are both offered, as long as the team they sit in is of type Purchase.

What does hide a user: (a) the team is of another type — M3M NOIDA's "Technical Team" is of type Planner, so its two members who are not also in "Purchase" never appear, whatever categories that team is mapped to; (b) the list shows at most 20 names, sorted by first name, until you type — in a big workspace a user with a late first name looks missing; (c) the user is inactive or was removed from the workspace.

Category and sub-category matter for a different thing: which PRs a user can see — and only when the workspace setting is_pr_teams_filtering_enabled is on. On UAT it is not set for M3M NOIDA (43569) and is false for M3M NOIDA LIMITED (43577), so there everyone sees every PR and the mapping changes nothing. When it is on, a parent-category team sees all its sub-categories (a PR carries one identifier per level), a sub-category team sees just that sub-category, and a team with a plant and a category sees only that plant's PRs of that category (section C).

2. "The user gets a notification that a PR was assigned, but no PR number and no redirect to the PR."

That is exactly what the code sends. The bell notification is built as title "PR line items have been assigned to you.", message "<assigner> assigned <n> PR line items to you." and deep link purchase-requisitions — a count, no PR number, and a link to the list. The dashboard follows that link to the Purchase Requisitions list; it already knows how to open a PR when the link is purchase-requisitions/<pr uuid>, but the backend never sends the id. The e-mail (only when the workspace has the pr_assignee_email setting — M3M NOIDA does not) does list PR numbers, but its button also opens the list.

Suggested fix for the developer: include the PR number(s) in the message, and when all assigned lines belong to one PR send purchase-requisitions/<uuid> as the deep link. One more trap when team filtering is on: a buyer can assign a line to a user whose teams do not cover that PR's category or plant; the assignment is accepted and the notification sent, but that user cannot see the PR at all (PRA-B09).

How it actually works

Assignee list (the person+ button and the '+' in a row)

GET /users/search?query=<typed>&filters={"team_types":["purchase"]} → active users of the workspace who are members of a team of type Purchase. Max 20 names, sorted by first name. The PR's category is not sent and not checked.

Assign

POST /purchase_requests/assign_pr_to_user {item_ids, user_id}. Checks: user has an active mapping in the workspace; every line fully open. Does NOT check team or category. Stamps assignee date, writes audit trail, sends notifications.

Who can see a PR

Only when is_pr_teams_filtering_enabled is true for the workspace. A PR carries identifiers: for each line, every category level of the product (parent and sub-category) × the plant of the line's location, plus plant-only and category-only forms. A user carries identifiers from ALL their teams (any team type): plant×category combinations if the team has both, else plant-only or category-only. Visible if any identifier matches. Super admins see all. On UAT: M3M NOIDA (43569) has no such setting → everyone sees everything; M3M NOIDA LIMITED (43577) has it false.

In-app notification

Title 'PR line items have been assigned to you.' Message '<assigner> assigned <n> PR line items to you.' Deep link 'purchase-requisitions' → the list. No PR number anywhere. The dashboard would open a PR if the link were 'purchase-requisitions/<pr uuid>'.

E-mail

Only if custom configuration pr_assignee_email is set (not set on M3M NOIDA in UAT). Subject 'New PR Assignments'; table with PR No and line; button → /purchase-requisitions?tab=active (list).

Automatic assignment by sub-category

Separate feature: custom configuration is_auto_pr_assignment_enabled with rules (fields such as materialSubcategoryName, first matching rule wins, fixed assignee_id). Not configured on M3M NOIDA in UAT.

Questions for product (decisions the tests cannot make)

  1. Should the assignee list be narrowed to users whose Purchase team covers the PR's category / plant — or at least warn when it does not? Today any Purchase-team member can be assigned any PR.
  2. Should users of other team types (Planner, Finance, Vendor management…) be assignable? Today only Purchase-type teams feed the list, while the API accepts any workspace user.
  3. Should the notification name the PR and open it? (Small backend change; the dashboard already supports the link.)
  4. Should assigning be refused when the assignee cannot see the PR (team filtering on)?
  5. Is a visible "unassign" control wanted? The API supports it; the screen has none.
  6. If the intent is "PRs go automatically to the person who owns the category", that is the separate rule-based auto-assignment setting, which M3M NOIDA does not have.

What to set up before running section C

  • Ops: set is_pr_teams_filtering_enabled = true on the test workspace (it is off on both M3M workspaces in UAT).
  • Teams on the workspace: T1 parent-category only; T2 sub-category only; T3 another category; T4 plant + sub-category (M3M's "Purchase" already is one); T5 plant only. One test user per team, QA e-mails only.
  • PRs whose lines are fully open, in known categories and plants (0110000195 = RM-STEEL under "0011", plant 12639, is a good one).
  • To test e-mails, set pr_assignee_email on the workspace and use QA mailboxes.
