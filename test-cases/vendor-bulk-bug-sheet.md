# Vendor bulk upload — bug sheet

**34 bugs reproduced on the UAT sandbox (1 critical, 9 high, 14 medium, 10 low), plus 1 found by reading the code and not yet run.** Clients: GMMCO LIMITED (47053, contactless ON, duplicate check on gst_no + address + pincode + account_group) and PROCOL DEMO (198678, contactless OFF, required extra fields). Latest run: 5 Oct 2026. Backend: procol-backend origin/main with PR 16267 (65728150bc).

Generated by `npm run vbu:bugsheet` from the bug registry (`prototype/config/vbuBugs.json`), the plain-language detail (`prototype/config/vbuBugDetails.json`) and the newest evidence record of every case (`prototype/data/evidence/`). Do not edit by hand.

## Where the buyer sees a result

- **The pop-up after Upload.** When the file can be read the server answers HTTP 200 `{"status":"success"}` at once and the screen shows the green **“Vendors Sheet Uploaded”**. The rows are checked afterwards, in the background. A refused file gets a red pop-up with the server's message (for example **“Invalid file format”**), and a server crash gets the red **“Internal Server Error”**.
- **The Bulk Upload history table:** Status, Total, Completed, Failed, Duplicate, Created, and a **Download Excel** button that is enabled only when Failed > 0.
- **The error sheet** from Download Excel: the failed rows, each with its message in an **Error** column.
- **The Vendors list**, under Vendors (active), Prospects or Rejected, with each vendor's record.

> How to read this test: rows that should NOT create a vendor carry a deliberate second mistake, Status = QA_TRIPWIRE. A row that gets past the rule under test therefore stops at “Invalid Status” and creates nothing, so “Invalid Status” in the error sheet means the rule under test let the row through. Every vendor the tests create is a test record: name QA_Platform_VBU_<stamp>_…, email qa_vbu_…@example.com, phone 0000000001, made-up tax numbers.

## BUG-01 · Critical — Two identical new vendors in one sheet are both created (same tax number + address, or same Vendor Code)

*Area:* Duplicate check · *Status:* open · *Found:* 2026-09-29 · *Test case(s):* VBU-151, VBU-211

**What the buyer does.** One sheet lists the same NEW supplier twice: (a) same tax number, address, pincode and Account Group, or (b) the same new Vendor Code. Only the company name and contact email differ. This is common in a large migration sheet.

**What should happen:**

- Pop-up: green 'Vendors Sheet Uploaded'.
- History: Total 2 · Completed 1 · Failed 1.
- Error sheet, second row: 'Vendor with this GST and address already exists' (a) or 'Vendor Code or GST Number is already taken' (b).
- Vendors: exactly ONE new vendor.

**What happens instead.** Sometimes both rows succeed (Completed 2, Failed 0), creating two vendors with the same tax number and address, or the same Vendor Code. It depends on timing: the two rows are checked in parallel. It failed on 29 Sep and 1 Oct (tax number) and on 5 Oct on PROCOL DEMO (Vendor Code), and passed on other runs.

**What the buyer sees.** Green “Vendors Sheet Uploaded”; the history shows Completed 2 · Failed 0. Nothing warns that the second row is a duplicate.

**Why it matters.** The duplicate check (gst_no, address, pincode, account_group on GMMCO) is skipped exactly when it matters most, in one big sheet. GMMCO's 11,000-row load is expected to hold many duplicates, and each one becomes a twin vendor that later flows to SAP.

**Cause in the code.** Each row runs in its own background job at the same time and the duplicate check only sees vendors already saved, so rows of one sheet never see each other.

**Where:** `app/workers/vendor_bulk_upload_master_worker_v2.rb:11-14; PR16267 app/services/invitation/send_service.rb:274-298`

**Suggested fix.** Drop or fail in-sheet duplicates by the configured key before queueing, or lock per workspace + tax number around the check and the insert.

## BUG-02 · High — GST rows fail 'Tax Type not configured for the selected Business Location' at random

*Area:* Tax number · *Status:* open · *Found:* 2026-09-29 · *Test case(s):* VBU-059

**What the buyer does.** A vendor with Business Location 'India', Tax Type 'GST' and a valid GSTIN.

**What should happen:**

- The row passes the tax check like any valid GSTIN.
- Error sheet: no tax message for this row.

**What happens instead.** On some days the row fails 'Tax Type not configured for the selected Business Location' for a perfectly valid GSTIN; on other days the same sheet passes. It failed on 29 Sep and on the morning of 30 Sep, and passed on the evening of 30 Sep, on 1 Oct and on 5 Oct, because a different 'India' row now comes first. The code is unchanged, so it can fail again at any time.

**What the buyer sees.** Error sheet: “Tax Type not configured for the selected Business Location” for a valid GSTIN, on the days the trap fires.

**Why it matters.** Whether ANY Indian GST vendor can be uploaded depends on which of the 37 'India' rows in the countries table the database returns first. 55 real rows failed this way in the 60 days before 29 Sep.

**Cause in the code.** Country.find_by(name: 'India') has no order or status filter. On 5 Oct 2026 the sandbox had 37 'India' countries; only ids 108, 270 and 299 have an active GST mapping. Which row the database returns first decides the outcome: on 29-30 Sep it was one without a mapping, on 5 Oct it was 299, so the same sheet passed.

**Where:** `app/services/validations/vendor_bulk_upload_validation_service_v2.rb:86-88; countries table (37 rows named India on 5 Oct 2026)`

**Suggested fix.** Look the mapping up through the active TaxTypeCountryMapping joined on country and tax type names; clean the duplicate countries; check production.

## BUG-03 · High — HTTP 500 when excel_data is an empty string

*Area:* File check · *Status:* open · *Found:* 2026-09-29 · *Test case(s):* VBU-003

**What the buyer does.** The upload is sent with an empty file (excel_data is an empty string, as when a 0-byte file is picked).

**What should happen:**

- Server: HTTP 422 {"error":{"code":15,"message":"Invalid file format"}}, the same answer a PDF or PNG gets.
- Pop-up: red 'Invalid file format'.
- History: no new job.

**What happens instead.** The server crashes: HTTP 500 {"status":500,"error":"Internal Server Error"}. The buyer sees a red 'Internal Server Error' pop-up.

**What the buyer sees.** Red pop-up “Internal Server Error”.

**Why it matters.** A crash instead of a clear message. The buyer cannot tell what is wrong with the file, and every attempt raises a server error alert.

**Cause in the code.** Only nil is checked; an empty string becomes a 0-byte file and the Roo error is not rescued.

**Where:** `app/controllers/api/v1/companies_controller.rb:209; lib/excel_sheet_utils.rb:2-13`

**Suggested fix.** Treat blank excel_data like missing; rescue every read error as 'Invalid file format'.

## BUG-07 · High — POC 2 problems: the row says 'failed' but the vendor was created and invited

*Area:* Second contact (POC 2) · *Status:* open · *Found:* 2026-09-29 · *Test case(s):* VBU-128, VBU-210, VBU-230

**What the buyer does.** A row with a valid main contact and a POC 2 that is wrong in one of three ways: (a) POC 2 - Full Name filled but its email blank, (b) POC 2 - Email Address filled but its name blank, or (c) the POC 2 email is the same as the main contact's.

**What should happen:**

- History: Failed 1, Created 0.
- Error sheet: 'Invalid Values for POC 2.' (a, b), or a clear message that POC 2 must be a different person (c).
- Vendors: NO vendor created and NO invitation sent, because a failed row creates nothing.
