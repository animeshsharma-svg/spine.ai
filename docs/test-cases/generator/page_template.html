Procol Sourcing Test Cases

Every case is written for a tester who has never used Procol: each click is named, each screen is described, and the expected result quotes the app's own message where the app has one. The rules come from the product's code and from runs on UAT; where the product has not settled a rule, the case says "record" instead of guessing.

Before you start

  • People. One buyer login, one approver (where a case needs approval), and the QA test vendors A, B and C (names start with QA_Platform, e-mails end with @example.com). Never invite a real supplier.
  • Two browsers. Keep the buyer in one browser and the vendor in another (or an incognito window) so both stay logged in.
  • Order. Run module 0 first: it makes the events later cases name, such as "the RFQ with two bids (A 100, B 90)".
  • Vendors. When a case names a vendor, add that vendor by search. When it names none, click "Invite Vendor" to add everyone mapped to the product.
  • "Record". Where the expected result says "record", write down exactly what happened instead of marking the case failed.
  • Excel. The same cases, in the same 13 columns as the PO Amendment sheet, are in docs/test-cases/Procol-Sourcing-Test-Cases-PR-to-PO.xlsx.
