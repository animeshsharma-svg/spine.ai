## Bucket C resolved (13 Nov, Animesh)
Recipe choice (`recipeForLibraryCase`): a case that CREATES the proposal or works on a DRAFT one starts from `closed_rfq_with_bid` (a draft proposal is arranged with `open_proposal`); only a case that says the proposal is submitted / in approval / awarded starts from `awarded_rfq`; a case whose own request is the withdraw is not withdrawn beforehand. Four written requests were paraphrases and are corrected in `data/case-fixes.json` (API-AWD-002 the real add_response body, API-AWD-004 the approval-workflows read, API-AWD-020 the event read, AWD-PROP-004 the same lot as the first proposal — its `lot_no:"1"` was another lot, which the app rightly accepted). Re-run on fresh events: API-AWD-001, -002, -004, -020 and API-EVDNFA-002 PASS (the refusal “The proposal has already been submitted” now lands where the case expects it); API-AWD-022 is an honest partial (the framework has no reject-through-approval call: `needsState`); API-DB-008 is couldn't tell (the plan's read-back names a withdraw-remark field the reply does not carry). The two 500s of the first pass (add_response / approval_workflows) were OUR wrong placeholder (`event_group_line_item_uuid` filled with the event group uuid), not product defects.
