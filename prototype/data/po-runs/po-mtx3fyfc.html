D__006 OPEN — P0 YES BE — All users PO a create with fields lands the PO in "Released", skipping its whole lifecycle confirmed · POST /api/fx_responses/create_row · decathlon
what we found · how to reproduce The UI creates an empty record (responses: []) and PATCHes fields in one at a time; that record comes back status "0" (Draft). Sending the same fields in a single create_row instead comes back status "3" (Released) — the suite never sends status at all, it is in skipFields. So a populated create silently skips Draft, In Approval and Submitted. A released PO has nothing left to approve, which is the real cause of the bare 422 "Invalid Approval" on submit. Not reproducible by hand: the UI cannot release a PO at creation. Repro: captured UI create_row (responses: 0) -> status "0" Draft; `npm run po -- --client decathlon` create_row (12 fields, no status) -> status "3" Released, record Z05kY2Rj
blocks the whole approval flow end to end; nothing downstream can be tested until it moves
D__007 OPEN — P1 NO BE — All users PO state_code is accepted then silently discarded confirmed · POST /api/fx_responses/create_row · decathlon
what we found · how to reproduce state_code is mandatory and was sent as a valid widget_data_mappings record uuid ("a1hnZE5k", the value existing POs carry). The create returns 200 and the field reads back absent. A mandatory field accepted and thrown away leaves the document permanently incomplete with no error to act on. Repro: create payload for record Z05kY2Rj included state_code; field_responses has no value for it
D__009 TO BE DISCUSSED — P1 NO BE — All users Approvals omitting app-version silently returns a reduced payload confirmed · GET /api/fx_responses/{uuid}/get_approvals · both
what we found · how to reproduce The platform selects a response serializer from the app-version header. With no such header it answers 200 but strips every step and approver uuid, so a document cannot be approved and the cause is invisible — the call looks successful. Same effect on the approval-flows list, which switches between numeric ids and encoded uuids. The suite now always sends app-version. Repro: measured: no header -> approver.uuid undefined; 9.4.349 -> uuid present
worked around in the suite by always sending app-version — decide whether the default should be the full payload
D__010 TO BE DISCUSSED — P1 NO BE — All users Approvals no way to ask which approval flow applies to a document confirmed · GET /api/approval_workflow/approval_flows · decathlon
what we found · how to reproduce Decathlon has 75 active p2p_create_po flows, every one conditional and several sharing the same name, so a flow cannot be identified by name. /approval_flows/applicable returns 570 "Approval Flow not found". The only way to learn the applicable flow is to write to the record and read approval_applicable + approvals back off the response. Repro: probed live; traced through the captured UI session
API gap rather than a defect — raised as a request
